# Архитектурные решения ClimbPass 3

## ADR-01: слои и технологии
Сохраняем ES modules и предметную модель схемы 2, без смены UI-фреймворка. Прикладной слой исполняет команды над копией графа; репозиторий атомарно пишет граф и outbox. Native IndexedDB: один object store records с атомарным графом/outbox/journal, транзакции и versionchange, без дополнительной обёртки. Node.js >=22.12, HTTP server и mysql2: небольшой same-origin backend без runtime-компиляции. MySQL 8: строка пользователя блокирует изменения его графа. Физическое представление графа JSON с явным порядком массивов, адресуемыми patch-единицами (особенно отметками), ревизиями и неизменяемыми публикациями. Это позволяет сохранить произвольные старые ID без преобразований и проверять весь граф действующим валидатором. Отдельные таблицы: пользователи, OAuth identities, allowlist, sessions, operations, changes, imports, migrations. Переход к отдельным таблицам предметных сущностей возможен без изменения протокола.

## ADR-02: конкурентные изменения
Операция содержит ID, изменения адресуемых единиц с before/after, календарь и время устройства. Сервер проверяет исходные значения и предметные переходы, применяет весь patch транзакционно под блокировкой пользователя. Разные этапы объединяются; одно и то же поле/черновик/публикация конфликтуют. Операция отметки также содержит guard состояния занятия, поэтому завершение не пропускает поздние правки. Удаление сохраняет tombstone (revision с отсутствующим value); старые операции не воскрешают запись. Cursor монотонен на пользователя. Change содержит целый граф: одна страница не разделяет предметную транзакцию. Операции и удаления бессрочны в v1; очистка без нового протокола запрещена. Исходные редакции конфликтов и оставшаяся очередь сохраняются локально. Синхронизации одного аккаунта сериализуются между вкладками отдельным Web Lock; локальные read/write используют короткий независимый lock, не удерживаемый на время сети. Транзакция IDB дополнительно проверяет поколение графа.

## ADR-03: календарь
DATE — календарная строка YYYY-MM-DD, не UTC. Новое посещение использует локальную дату устройства в момент действия; операция содержит IANA timezone и эту дату. Сервер проверяет лимиты/срок относительно даты действия, допускает доставку после окончания срока. Часовой пояс не меняет ранее сохранённые даты. Это доверенный календарь пользователя, не система оплаты: дату не сверяем с серверным сегодняшним днём. Изменения часового пояса фиксируются в операции.

## ADR-04: вход и изоляция
Google OIDC Authorization Code + PKCE/state/nonce. jose проверяет подпись ID token, issuer, audience, срок и nonce; обязательны verified email и enabled allowlist. Сессии серверные, opaque token в HttpOnly SameSite=Lax Secure cookie, хранится только хеш. Origin + CSRF на изменениях, лимит тела и частоты. Allowlist проверяется на каждом API-запросе. Session token не попадает в клиентские хранилища. База на user ID, вход другого пользователя открывает другую базу. Перед выходом проверяются очередь и конфликты. Пользователь может синхронизировать изменения либо подтвердить выход с сохранением очереди на устройстве в прежнем аккаунте. Офлайн отзыв не удаляет уже скачанные данные.

## ADR-05: перенос истории и выпуск

Перенос прежней истории выполняется администратором серверным инструментом, после проверки владельца, preview и резервной копии. Исходник не меняется и не публикуется; импорт записывается одной идемпотентной операцией с проверкой курсора. Существующие программы сохраняются, непустая история автоматически не заменяется. Пользовательского интерфейса для JSON нет. Совместимые парсеры исходных форматов остаются внутренними инструментами, а не пользовательским сценарием.

Сборка копирует разрешённые ресурсы в dist, SW кеширует только оболочку. API требует protocolVersion=1. Изменения master публикуются через GitHub Actions после проверок; readiness сверяет точную content-version. Эксплуатационные процедуры и границы кодового отката описаны в [operations.md](operations.md).
