# Техническое устройство ClimbPass 3

## Слои

- `js/domain/model.js`: чистая модель схемы 2, валидация, legacy migration. `runtime.js`: подменяемые календарь/часы/ID. Предметные модули `passes.js`, `programs.js`, `workouts.js`, `stages.js` не импортируют UI, сетевой транспорт или конкретную БД.
- `js/store.js`: совместимый фасад прежнего localStorage-репозитория для старых тестов/инструментов; новый UI его load/write не вызывает.
- `js/data/graph.js`: адресуемые единицы, ревизии, guards, atomic patch и независимая серверная проверка переходов. Версия протокола 1.
- `js/data/local.js`: IndexedDB v1, запись графа/outbox/import journal в одной readwrite-транзакции, optimistic generation для нескольких вкладок.
- `js/data/migration.js`: четыре исходных формата, предварительный отчёт, raw SHA-256, сохранение порядка и детерминированное переименование ID при присоединении.
- `js/data/sync.js`: API transport, Web Locks, push до pull (для потерянного ответа после commit), повтор с задержкой, обработка сессии и конфликтов, курсор без обратного хода.
- `js/app.js`: прикладной mutate pipeline и экраны; `js/ui.js`: доступное подтверждение через native modal dialog.
- `server/`: same-origin HTTP, Google OIDC, сессии, MySQL repository и миграции. В production раздаётся только allowlist `dist/release.json`.

## Физическая модель

MySQL хранит полный валидированный граф пользователя в JSON, порядок — массивами, календарные даты — строками YYYY-MM-DD без преобразования в UTC. Пользовательская строка блокируется FOR UPDATE на время каждой атомарной операции. Межпользовательские ID могут совпадать, поскольку графы изолированы владельцем. ID владельца никогда не берётся из тела запроса. Серверные таблицы: allowed_users, users, oauth_identities, sessions, oauth_attempts, operations, changes, imports, schema_migrations.

Каждая предметная единица имеет ключ (`passes/id`, `visits/id`, `workouts/visitId`, `marks/visitId/stepId` и т. д.), before/after и revision — ID последней принятой операции. Ревизии удалённых ключей сохраняются. Снимки/содержание валидируются целиком; опубликованные версии при обычных изменениях неизменяемы. Mark отдельно адресуем: разные этапы не конфликтуют; lifecycle guards связывают mark с состоянием занятия и завершение со всеми marks. Завершение/возобновление после изменения другого устройства требует явного решения.

`operations(user_id,operation_id)` содержит digest запроса и прежний результат: повтор с изменённым телом отклоняется. Graph, revisions, operation receipt, change cursor и import receipt записываются одной SQL-транзакцией. `changes` содержит атомарные снимки. Pull возвращает последний целый снимок без пагинации: связанная операция никогда не разделяется на страницы. В этой версии история, receipts и tombstones не удаляются. Полный pull — сознательный выбор малого личного приложения; рост данных требует нового протокола/пагинации, а не удаления старых служебных записей.

## Локальная запись и несколько вкладок

База `climbpass-user-<userId>` содержит store records/root: state, confirmed, revisions/localRevisions, cursor, outbox, conflicts, imports и generation. Граф/outbox атомарны. Web Locks сериализует короткие локальные read/write между вкладками; отдельный lock защищает сетевой цикл. Локальные действия не ждут HTTP-ответов. Generation дополнительно отклоняет устаревшую запись. BroadcastChannel сообщает вкладкам об изменении. Пока пользователь вводит текст, sync не перестраивает DOM; ошибка сохранения удерживает поле и блокирует уход/отметку. Экспорт включает несохранённые значения отдельно.

При 409 клиент сохраняет весь локальный граф и оставшуюся очередь плюс отдельный confirmed. Изменения замораживаются до решения. При выборе локальной редакции создаётся явный restore с expectedCursor; при выборе сервера после скачивания копии очередь снимается. Просмотр показывает обе редакции полностью; это консервативное разрешение всей ожидающей ветки, а не автоматическое слияние текстов.

## Импорт

Источники: legacy array, v2 state, formatVersion 2 envelope, raw strings обоих localStorage-ключей; дополнительно аварийный формат 3 нового приложения. При наличии испорченного v2 fallback к legacy запрещён. Нормализация типов этапов использует stages.js. Синтетические даты добавляются только новым исходным программам, историческим абонементам/посещениям время создания не приписывается.

Attach к пустому аккаунту сохраняет старые строковые ID. Join к существующей истории создаёт детерминированный namespace от checksum и полный ID map; посещения не дедуплицируются по дате. Невалидное объединение (например, два active pass) не активируется. Restore — отдельная cursor-guarded замена, которая включает удаление прежних единиц и распространяется в sync. ID операции и journal сохраняются до сети; перезапуск продолжает прежний импорт. Журнал отдельно фиксирует localCompletedAt и serverCursor.

## Ресурсы и обновления

`npm run build` копирует allowlist в dist, вычисляет content hash, создаёт release.json и полный SW shell. Локальные Onest/Material Symbols и лицензии входят в shell. API/OAuth/health обходят SW. Установка кеша атомарно завершается только после загрузки всего shell; принудительной активации над открытым редактором нет. Версия в health включает git SHA и хеш ресурсов, поэтому незакоммиченные сборки различимы.

Старые hash-маршруты сохранены; см. screens.md. Storage schemaVersion 2 предметного документа не совпадает с IndexedDB version 1: это независимые версии. Любое будущее изменение IDB выполняется в onupgradeneeded; blocked/versionchange показывают пользователю необходимость закрыть вкладки.

## Проверки и ограничения

Запуск и доказательства — acceptance.md. Тесты не включают реальные пользовательские файлы: history.json игнорируется и не копируется в dist. `scripts/verify-history.js` проверяет выбранную копию через IndexedDB и сервер только на *_test БД. Production/OAuth/iOS/Android требуют отдельного окружения и ручной приёмки.
