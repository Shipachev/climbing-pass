# Техническое задание на рефакторинг ClimbPass

Дата: 02.11.2026. Версия ТЗ: 1.1.

Редакция 1.1: включён редизайн на основе локальной папки `design system/`.

Статус: требования к реализации; выбор отдельных технологий выполняется на архитектурном этапе. Документ не означает, что описанные изменения уже реализованы.

## 1. Цель и границы

Перевести ClimbPass из локального однопользовательского PWA в приложение с учётными записями, серверным хранением, управляемыми миграциями и синхронизацией между устройствами. Сохранить существующие данные и предметные правила, обновить интерфейс по дизайн-системе ClimbPass и сохранить возможность работать без сети после первоначальной настройки.

Архитектура Wally используется как источник опыта, а не как обязательный образец. Повторять её решения ради единообразия не требуется. Каждая технология и каждый заимствованный механизм должны решать конкретную задачу ClimbPass.

В объём входят:

- пользователи, вход через Google, управление разрешённым доступом;
- серверная БД, миграции и контроль принадлежности данных;
- локальное структурированное хранилище и очередь изменений;
- синхронизация и разрешение конфликтов;
- перенос всех существующих данных и совместимость резервных копий;
- редизайн всех действующих экранов и новых сценариев авторизации, миграции и синхронизации по разделу 16;
- адаптация PWA, проверок и процесса выпуска;
- эксплуатационная и пользовательская документация.

В объём не входят Apple OAuth, публичная самостоятельная регистрация, совместные абонементы, платежи, новые типы тренировок, полноценный интерфейс администратора и тёмная тема. Их добавление требует самостоятельных требований.

## 3. Фактическая модель данных

### 3.1. Хранилище

Основной источник — JSON-документ в `localStorage` под ключом `climb_pass_v2`. Корень содержит `schemaVersion: 2` и массивы `passes`, `visits`, `programs`, `versions`, `drafts`.

Запись выполняется после валидации целого состояния. UI меняет копию состояния и заменяет данные в памяти только после успешной записи. Кеш Service Worker содержит ресурсы приложения, а не пользовательские записи.

### 3.2. Сущности и поля

| Сущность | Поля |
| --- | --- |
| `passes[]` | `id`, `start`, `end`, `total`, `status: active/archived` |
| `visits[]` | `id`, `passId`, `date`, необязательный `workout` |
| `programs[]` | `id`, `currentVersionId`, `archived: boolean` |
| `versions[]` | `id`, `programId`, `number`, `savedAt`, `content` |
| `drafts[]` | `programId`, `baseVersionId`, `updatedAt`, `content` |

Вложенный `workout`:

- `id`, `programId`, `versionId`, `versionNumber`;
- `content` — копия содержания опубликованной версии;
- `status: active/completed`, `startedAt`, `completedAt`;
- `marks`: объект, ключом которого является ID этапа, значением — `{status, note}`;
- статус отметки: `pending/done/skipped`, заметка — строка.

Структура `content`:

| Уровень | Поля и типы |
| --- | --- |
| Программа | `title`, `goal`, `notes` — строки; `duration` — число либо `''`/`null`; `sections` — массив |
| Раздел | `id`, `title`, `duration` — строки; `steps` — массив |
| Этап | `id`, `title`, `instructions`, `duration`, `volume` — строки; `optional` — boolean; `type` — тип этапа |

Типы этапа: `warmup`, `training`, `cooldown`. Старое состояние может не содержать `type`; текущий код добавляет его в версии, черновики и снимки по правилам `js/stages.js`, не повышая `schemaVersion`.

### 3.3. Семантика значений

- `start`, `end`, `date` — календарные строки `YYYY-MM-DD`, не моменты времени.
- `savedAt`, `updatedAt`, `startedAt`, `completedAt` — временные отметки; новые значения генерируются в ISO UTC.
- Точное время регистрации посещения и даты создания старых абонементов неизвестны.
- `duration` разделов и этапов, `volume` — произвольный текст. Не преобразовывать их принудительно в числа.
- Новые ID — UUID, но действующие данные включают `legacy-*`, `program-1`, `program-1-v1` и другие допустимые строковые ID.
- Порядок массивов значим для отображения и разрешения совпадений при сортировке. При переносе в БД его необходимо представить явно.

## 4. Сохраняемые предметные правила

### 4.1. Абонементы и посещения

1. Не более одного действующего абонемента на пользователя.
2. Новый или редактируемый абонемент имеет лимит 1, 4 или 8; по умолчанию 8. Исторические положительные целые лимиты сохраняются.
3. `start` и `end` обязательны, `end >= start`. Новый абонемент не может уже истечь.
4. Дата окончания включается в срок. Абонемент завершён, если `end` раньше текущего дня либо использован весь лимит.
5. Использованное количество — число неудалённых посещений абонемента. Отдельного изменяемого счётчика использованных проходов нет.
6. Регистрация посещения доступна только по действующему, начавшемуся, не завершённому абонементу и создаёт запись на текущий день.
7. Несколько посещений одного дня допустимы. Повтор требует подтверждения в UI, а не запрета уникальным индексом.
8. Проход расходуется при регистрации посещения, а не при запуске или завершении тренировки.
9. Разовое посещение представлено абонементом с `total: 1`.
10. Редактирование лимита не допускает значения меньше уже использованного. Изменение может завершить абонемент после подтверждения.
11. Удаление посещения удаляет связанную тренировку и результаты как одну предметную операцию.
12. Нельзя удалить посещение архивного абонемента, пока есть действующий. Если действующего нет и после удаления абонемент снова доступен, он становится активным.
13. Самостоятельное удаление абонемента сейчас отсутствует; не добавлять его автоматически при создании CRUD.

Правила создания не должны ретроспективно портить историю. Текущий валидатор, например, не требует попадания исторической даты посещения в срок абонемента. Старые записи с такими особенностями сохранять; обнаруженные несоответствия отражать в отчёте импорта.

### 4.2. Программы и тренировки

1. Посещение может не иметь тренировки; на одно посещение приходится не более одной тренировки.
2. Повторный запуск возвращает уже существующую тренировку и не списывает проход повторно.
3. Для нового занятия берётся последняя опубликованная версия неархивной программы.
4. Опубликованные версии неизменяемы. Номера последовательны с единицы, `currentVersionId` указывает на последнюю версию.
5. Снимок содержания занятия соответствует связанной версии. Новая публикация не изменяет старые занятия.
6. Восстановление старой версии создаёт новую публикацию, а не переписывает историю.
7. Один черновик на программу; хранится отдельно от публикаций. Допускается незавершённое содержание, включая значения, запрещённые при публикации.
8. Публикация требует непустого названия программы, хотя бы одного этапа, непустых названий разделов и этапов, корректных длительностей по действующим правилам `validateContent`.
9. Завершение возможно с `pending` и `skipped`; UI показывает подтверждение с итогами.
10. Завершённое занятие не редактируется без возобновления. Возобновление сохраняет отметки и заметки, переводит статус в `active`, очищает `completedAt`.
11. Архив программы или абонемента не блокирует продолжение существующего занятия.
12. Новые личные заметки доступны только этапам `training`. Прежние заметки других типов сохраняются при переносе.
13. Подсказка из предыдущего занятия использует ту же программу и стабильный ID этапа. Нельзя подставлять более старую непустую заметку вместо пустой заметки непосредственно предыдущего занятия.
14. Последнее завершение программы вычисляется по `completedAt` завершённых занятий всех её версий, включая архивные абонементы; возобновлённые занятия исключаются.

При совпадениях текущий порядок истории использует дату, время запуска и индекс записи в массиве. Перенос должен сохранить эквивалентный стабильный порядок, включая посещения без тренировки.

## 5. Архитектурные требования и выбор технологий

### 5.1. Обязательные свойства

- Предметная логика не зависит от UI-фреймворка, ORM, сети и конкретного хранилища.
- UI работает через прикладные операции и репозитории, не обращается к БД напрямую.
- Локальная запись и добавление в очередь синхронизации выполняются одной транзакцией.
- Действие пользователя сохраняется локально без ожидания сервера. UI различает локальное сохранение и подтверждение сервером.
- Сервер проверяет данные и принадлежность независимо от клиента; подтверждённое серверное состояние является общим источником для устройств.
- Все обычные изменения проходят единый путь синхронизации. Импорт может быть специальной транзакционной операцией, но должен попадать в тот же поток изменений для остальных устройств.
- Для календаря, времени, ID, хранения и транспорта предусмотрены заменяемые зависимости.
- Ошибка записи не должна выглядеть как успешное сохранение.

### 5.2. Технологические ограничения и решения

Серверное хранилище: MySQL с управляемыми версионированными миграциями. Google OAuth — первый способ входа.

Кандидаты, требующие обоснования на архитектурном этапе:

| Область | Кандидат | Критерий решения |
| --- | --- | --- |
| Локальная БД | IndexedDB с Dexie | Транзакции, миграции, поддержка целевых браузеров |
| Серверная модель | Prisma | Проверяемые миграции и удобство работы с MySQL |
| Клиент | Существующий модульный JS либо TypeScript и UI-фреймворк | Сложность нового интерфейса, стоимость переноса, сопровождение; JSX-компоненты дизайн-системы не делают React обязательным |
| Сервер | Отдельный backend либо Next.js | Простота эксплуатации и надёжная офлайн-оболочка |
| Авторизация | Auth.js либо подходящая библиотека выбранного сервера | Безопасный OAuth и жизненный цикл сессии |
| Сессии | JWT либо серверные сессии | Отзыв доступа, эксплуатационная простота |
| PWA | Адаптация текущего SW либо Serwist | Совместимость, контролируемое обновление и кеширование |
| Выпуск | Процесс на VPS, при необходимости Docker | Воспроизводимость, откат и изоляция |

Зафиксировать выбор и причины в коротких архитектурных решениях до реализации зависимых этапов. Не считать Next.js, React, Auth.js без Prisma Adapter, Serwist, Docker или тестовый стек Wally обязательными. Особенность Wally с именем финансовой модели `Account` к ClimbPass не относится.

## 6. Целевая логическая модель

Названия физических таблиц и типы ORM уточняются при проектировании без потери перечисленной семантики.

| Сущность | Поля и требования |
| --- | --- |
| `User` | Серверный ID, нормализованный уникальный email, имя при наличии, технические даты |
| OAuth-идентичность | Уникальная связь провайдера и его идентификатора с пользователем; физическое представление зависит от выбранной авторизации |
| `AllowedUser` | Нормализованный email, enabled, технические даты; серверное управление доступом |
| `Pass` | Владелец, `start`, `end`, `total`, `status`, стабильный порядок |
| `Visit` | Владелец, ссылка на абонемент, `date`, стабильный порядок |
| `Program` | Владелец, `currentVersionId`, `archived`, порядок каталога |
| `ProgramVersion` | Владелец, программа, `number`, `savedAt`, неизменяемый `content` |
| `ProgramDraft` | Владелец, программа, `baseVersionId`, `updatedAt`, `content` |
| `Workout` | Владелец, уникальный `visitId`, программа, версия, `versionNumber`, снимок `content`, статус, времена |
| `WorkoutMark` | Тренировка, ID этапа, статус, заметка; отдельная адресуемая единица изменения |
| Служебные сущности | Очередь клиента, дедупликация операций на сервере, курсор, последовательность изменений, журнал импорта и соответствие ID |

Допускается иное физическое представление отметок при сохранении независимой синхронизации этапов. Содержание версий, снимков и черновиков рекомендуется хранить JSON с проверяемой схемой; порядок разделов и этапов сохранять.

Обязательные ограничения:

- владелец сущности и всех её связей совпадает;
- уникальны `(programId, number)`, программа черновика, `visitId` тренировки, `(workoutId, stepId)`;
- дата посещения не уникальна;
- единственный активный абонемент и остаток проходов проверяются транзакционно при конкурирующих запросах;
- `number` публикации отделён от технической версии конкурентного изменения;
- изменяемые синхронизируемые записи имеют ревизию, порядок серверных изменений и признак удаления либо эквивалентные механизмы;
- удаления передаются всем устройствам и не отменяются поздней повторной отправкой старой записи;
- известные исходные времена сохраняются; неизвестные не подменяются временем импорта;
- календарные даты хранятся как DATE либо эквивалентное значение без преобразования в UTC-момент;
- исходные строковые ID сохраняются либо имеют полную таблицу соответствия; межпользовательские совпадения не создают конфликтов;
- исходные программы создаются только при первичной инициализации, обновление seeds не переписывает пользовательские версии.

## 7. Вход, безопасность и локальная изоляция

1. Первый вход и получение данных на новом устройстве требуют сети. После успешной настройки ранее загруженные данные доступны офлайн.
2. Google OAuth использует безопасный redirect-flow, проверку ответа провайдера и подтверждённого email. Пароли в ClimbPass не добавляются.
3. Сервер определяет владельца по проверенной сессии, игнорирует попытки задать чужой `userId` и проверяет все связанные ID.
4. Разрешение доступа проверяется при входе и чувствительных API-запросах. Отозванный доступ запрещает серверное чтение и запись на следующем запросе.
5. Отзыв доступа на сервере не означает гарантированного удаления уже скачанных данных с офлайн-устройства; это ограничение описывается в документации.
6. Потеря сети и неуспех проверки сессии не очищают локальные данные и не гасят офлайн-интерфейс. Истечение сессии приостанавливает синхронизацию до повторного входа.
7. Локальные базы и очередь изолированы по пользователю. Смена аккаунта не показывает данные предыдущего пользователя и не отправляет его операции от нового аккаунта.
8. Перед выходом проверяются ожидающие изменения: синхронизация, экспорт либо явное решение пользователя об удалении. Тихая потеря очереди запрещена.
9. Секреты OAuth и БД находятся только на сервере. Токены провайдера не хранятся в localStorage/IndexedDB.
10. Для API предусмотрены проверка входных данных, защита от CSRF с учётом выбранных сессий, ограничение размеров запросов, rate limiting и безопасные HTTP-заголовки.
11. Логи не содержат содержание тренировок, заметки, резервные копии, токены и секреты.

## 8. Синхронизация и конфликты

### 8.1. Протокол

- У каждой операции есть стабильный идентификатор для повторной отправки без повторного эффекта.
- Клиент хранит очередь до подтверждения сервера; перезапуск приложения её не теряет.
- Порядок изменений между сущностями задаётся серверным курсором, отдельно от ревизии конкретной записи.
- Изменения и продвижение курсора применяются локально атомарно. Пагинация не пропускает связанные изменения.
- Повторные запросы, задержки сети и ответы не по порядку не откатывают более новое состояние.
- Сетевые ошибки повторяются с задержкой; ошибки авторизации и предметные конфликты различаются.
- Возвращение сети запускает синхронизацию без принудительной перезагрузки интерфейса.
- Обработать несколько вкладок: они не должны терять изменения и создавать независимые дубли одной операции.
- Срок хранения удалений и обработанных операций должен быть согласован с политикой долгого офлайна. Устаревший клиент проходит полную сверку без потери собственной очереди.

### 8.2. Предметная политика

| Конфликт | Требуемый результат |
| --- | --- |
| Повторная доставка операции | Тот же результат без дублей |
| Два устройства расходуют последний проход | Сервер принимает одну операцию; другая сохраняется как видимый конфликт для решения пользователем |
| Два действующих абонемента | Инвариант сохраняется; отклонённая локальная запись не исчезает молча |
| Две публикации от одной базовой версии | Сервер назначает последовательные номера; конфликтующие правки сохраняются и требуют разрешения |
| Два черновика одной программы | Не затирать правки целиком; сохранить конфликтующую редакцию для выбора или объединения |
| Разные программы в одном посещении | Одна подтверждённая тренировка, явный конфликт второго запуска |
| Разные этапы одного занятия | Независимое объединение при отсутствии иных конфликтов |
| Одна заметка или статус этапа изменены одновременно | Сохранить обе конфликтующие редакции и предложить выбор; не объединять текст автоматически |
| Завершение/возобновление против правок | Проверка ревизии занятия; не менять завершённое занятие скрытно |
| Удаление посещения против его редактирования | Удаление блокирует автоматическое воскрешение; конфликтующие правки доступны для экспорта или явного восстановления |

Серверные и локальные атомарные операции: регистрация посещения с изменением доступности абонемента; удаление посещения со связанными результатами и пересчётом статуса; публикация с переключением текущей версии; запуск занятия со снимком и полным набором отметок.

### 8.3. Календарь

При регистрации сохранять выбранную на устройстве локальную календарную дату, не заменять её датой UTC-сервера. Проверять доступность абонемента относительно этой даты и согласованной политики календаря пользователя. Часовой пояс, допустимость задержанной офлайн-доставки и поведение при смене пояса фиксируются отдельным архитектурным решением до реализации серверных проверок.

Не отклонять посещение только потому, что к моменту доставки серверу наступил следующий день или абонемент уже истёк. Конкурентное исчерпание лимита обрабатывается как конфликт.

## 9. Перенос существующих данных

### 9.1. Поддерживаемые источники

1. `localStorage.climb_pass`: массив `{id: integer, start, end, total, status, visits: string[]}`.
2. `localStorage.climb_pass_v2`: полный документ состояния схемы 2.
3. Полный экспорт `{formatVersion: 2, exportedAt, state}`.
4. Аварийный экспорт `{climb_pass, climb_pass_v2}`, значения которого — сырые строки или null. Сейчас штатный импорт его не принимает; новый механизм восстановления должен поддержать явно.

Существующая миграция legacy создаёт `legacy-{id}` и `legacy-{id}-visit-{index}`, сохраняет дубли дат, добавляет начальные программы и оставляет старый ключ. При наличии v2 используется он; повреждение v2 не означает разрешения молча заменить его старым состоянием.

### 9.2. Последовательность

1. Снять доступную для скачивания исходную копию обоих ключей, указать origin, формат и контрольную сумму. Не очищать хранилище.
2. Разобрать выбранный источник, проверить ссылки, даты, статусы, лимиты, версии и снимки. При повреждении остановить перенос, показать конкретные ошибки, сохранить исходные байты.
3. Привести данные к нормализованной модели с сохранением старых ID, порядка и семантики. Для отсутствующих типов этапов использовать действующее преобразование совместимости.
4. После входа явно предложить присоединение анонимных локальных данных к выбранному аккаунту. Не выполнять присоединение к любому вошедшему аккаунту автоматически.
5. Создать стабильный идентификатор переноса, таблицу соответствия ID и журнал этапов. Контрольная сумма обнаруживает повтор исходного файла, но сама по себе не доказывает тождество разных историй.
6. Сохранить локальный граф одной транзакцией вместе с отметкой завершения этапа. Ошибка не оставляет частично активированную новую БД.
7. Выполнить идемпотентный серверный импорт с проверкой владельца. При разбиении на порции использовать промежуточное состояние и атомарную финализацию; незавершённый импорт не появляется как полноценная история.
8. Сверить количество сущностей, соответствие связей, лимиты, порядок, версии, снимки, черновики, отметки и заметки. При преобразовании сравнивать нормализованные значения, учитывая таблицу соответствия ID.
9. Отдельно показывать завершение локальной миграции и серверной загрузки. Сохранить исходный localStorage для восстановления; последующая очистка — отдельное явное действие.

### 9.3. Совпадения и неоднозначности

- `program-1`, `program-1-v1` и `legacy-*` могут совпадать на разных устройствах при разном содержимом. Не выполнять слепой upsert по такому ID.
- Посещения одной даты не объединять автоматически.
- Полностью одинаковые версии и снимки можно сопоставлять только по формально определённой процедуре; пользовательские редакции не заменять seeds.
- При существующей облачной истории сначала показать предварительный отчёт: новые записи, совпадения, конфликты и итоговые количества.
- Если однозначное слияние невозможно, сохранить оба набора во временной области и запросить решение; не активировать состояние, нарушающее ограничения.
- Повтор импорта после сбоя не создаёт новые сущности. Изменённый файл не считается автоматически безопасным повтором.
- Синтетическое время импорта хранить отдельно от неизвестного времени создания исторической записи.

## 10. Экспорт, импорт и восстановление после рефакторинга

Полная копия должна содержать всю предметную историю, черновики, версии, снимки, отметки, заметки и стабильный порядок, иметь версию формата и дату экспорта. Секреты и OAuth-токены исключаются. Ожидающие изменения и конфликты должны быть восстановимы: в полной копии либо в отдельном явно обозначенном аварийном экспорте.

Новый импорт поддерживает старый массив и формат 2. Неизвестную новую версию отклоняет с понятным сообщением. Повреждённый файл не изменяет действующие данные.

Существующее полное замещение сохранить как явно названный сценарий восстановления, но выполнять его для аккаунта транзакционно с предварительным отчётом и подтверждением. Замена должна распространять удаления на другие устройства. Различать восстановление с заменой и присоединение локальной истории; не превращать прежнюю замену в неявное слияние.

Экспорт должен быть доступен без сети и при неудаче синхронизации. Серверные резервные копии и проверка их восстановления дополняют пользовательский экспорт.

## 11. PWA, эксплуатация и выпуск

- После первой успешной настройки доступны офлайн-перезапуск, история, регистрация посещений, тренировки, черновики и экспорт в рамках загруженных данных.
- API, OAuth и пользовательские ответы не кешируются Service Worker. Кеш оболочки не смешивает данные аккаунтов.
- Новая версия приложения не сочетает несовместимые ресурсы и не теряет локальную очередь.
- Обновления IndexedDB обрабатывают блокировку старой вкладкой, закрывают устаревшие соединения и показывают понятное состояние ожидания, включая iOS PWA.
- Изменение origin требует отдельного переноса: новый сайт не может читать localStorage старого origin. При смене адреса до переключения обеспечить экспорт либо переходный выпуск на старом адресе.
- Определить совместимость старого и нового клиента с API; не допускать запись старым клиентом в неподдерживаемую схему.
- Расширить существующий workflow: проверки, сборка при необходимости, серверные миграции, выпуск, проверка живости и фактической версии.
- Производственная миграция запускается в контролируемом порядке, а не конкурентно каждым экземпляром приложения.
- Предусмотреть резервную копию БД, восстановление, журнал ошибок, проверку доступности БД и документированный откат. Откат приложения не должен требовать разрушительного отката пользовательских данных.
- Не переносить специфичные для Wally обходы ошибок драйвера и watchdog без проверки их необходимости в выбранной конфигурации.

## 12. Этапы реализации

| Этап | Результат и условие завершения |
| --- | --- |
| 1. Фиксация исходной модели | Контрольная ревизия, фикстуры legacy/v2, каталог инвариантов, карта экранов и состояний редизайна, архитектурные решения по стеку, календарю и сессиям |
| 2. Разделение слоёв | Предметные операции отделены от UI, времени и хранилища; текущие сценарии сохраняются |

| 4. Сервер и авторизация | MySQL, миграции, вход, allowlist, ownership, изоляция аккаунтов и серверные инварианты |

## 13. Проверки и критерии приёмки

### 13.1. Сохранение поведения

- Все правила раздела 4 проверены автоматизированными предметными тестами; действующие 20 тестов сохранены или перенесены с эквивалентным смыслом.
- Проверены абонементы на 1/4/8, исторический иной лимит, граничные даты, повтор одного дня, удаление и возврат в активные.
- Проверены версия, черновик, снимок, архив, возобновление, пустая предыдущая заметка и стабильный порядок совпавших записей.

### 13.2. Миграция

- Поддержаны все четыре источника из раздела 9.
- Повтор и прерывание на каждом сохраняемом этапе не создают дублей и не теряют данные.
- Проверены повреждённый JSON, неверные связи, исчерпание места, отсутствие типов этапов, совпадающие ID разных устройств, существующая облачная история.
- После переноса совпадают все предметные данные, включая дубли дат и порядок; исходная копия доступна.

### 13.3. Сервер и синхронизация

- Чужие данные недоступны через чтение, мутации, импорт и подстановку связанных ID.
- Отключение allowlist блокирует следующий серверный запрос.
- Повтор операции не меняет результат повторно; сбой между записью и ответом не создаёт дубль.
- Проверены все конфликты раздела 8 на двух независимых устройствах/контекстах.
- Pull с пагинацией, удаления и восстановление после долгого офлайна сходятся к согласованному состоянию без потери неподтверждённых правок.
- Конкурентное расходование последнего прохода и создание активных абонементов не нарушают серверные ограничения.

### 13.4. Браузер и выпуск

- E2E: вход → перенос → посещение → тренировка → заметка → завершение → второе устройство.
- Офлайн: перезапуск → посещение и правки → повторный запуск → восстановление сети → подтверждённая синхронизация.
- Проверены истечение сессии, выход с очередью, смена аккаунта и несколько вкладок.
- Проверены установленная iOS PWA и Android Chrome/PWA, обновление прежней версии, блокировка миграции IndexedDB и отсутствие пользовательского API в SW-кеше.
- Выполнено тестовое восстановление серверной копии и откат выпуска; версия в приложении позволяет подтвердить фактический деплой.

### 13.5. Редизайн

- Выполнены требования раздела 16 и матрица состояний всех экранов.
- Представлены сравнительные снимки эталонов и реализации на ширине 390px, а также проверки 320, 360, 430, 768 и 1280px.
- Проверены длинные тексты, произвольное число разделов и этапов, несколько незавершённых занятий, пустые данные и исторический лимит вне 1/4/8.
- На iOS и Android проверены клавиатура, safe area, свайп, прокрутка, модальные листы и офлайн-загрузка шрифтов/иконок.
- Выполнены ручные проверки клавиатурой, скринридером и при увеличении текста до 200%; сохранены доступность действий и читаемость.
- Прототипные ограничения из раздела 16.10 не попали в предметную модель.

Приёмка подтверждается отчётом с выполненными сценариями и известными ограничениями. Успешные unit-тесты или push сами по себе не означают завершения выпуска.

## 16. Техническое задание на редизайн

### 16.1. Цель, источники и приоритет требований

Обновить приложение в визуальном направлении «Страва» из локальной дизайн-системы: спортивный, плотный, высококонтрастный мобильный интерфейс для использования между подходами. Основной путь — открыть занятие, прочитать задание, отметить этап и сохранить заметку — должен оставаться коротким и доступным одной рукой.

| Источник в `design system/` | Применение |
| --- | --- |
| `readme.md`, `SKILL.md` | Принципы бренда и использования материалов |
| `tokens/colors.css`, `typography.css`, `spacing.css`, `fonts.css`, `base.css` | Палитра, семантические переменные, шрифты, размеры и поведение |
| `guidelines/*.html` | Проверяемые правила цвета, типографики, касаний и текстов |
| `components/` — JSX, типы и `*.prompt.md` | Внешний вид и контракты компонентов |
| `ClimbPass Страва.dc.html` | Композиция восьми состояний/экранов направления |
| `ui_kits/climbpass/` | Демонстрация переходов главной, занятия, программ, редактора, истории и настроек |

Ссылка на `ClimbPass Directions.dc.html` есть в материалах, но сам файл в исследованной папке отсутствует; реализация не должна зависеть от него.

Новые требования доступности уточняют макеты. Любое необходимое визуальное отклонение фиксировать с причиной и снимком результата.

Компоненты и прототип являются исходными материалами для адаптации. Их наличие не означает готовности к production и не определяет обязательный UI-фреймворк. Допускается перенос внешнего вида и контрактов на выбранную технологию.

### 16.2. Цвет, типографика и геометрия

| Основа | Белый `#FFFFFF`, основной текст и чёрный главный блок `#0F0F0F` |

| Рамки | Карточки 1px `#E3E3E3`; поля и сильные контуры по компонентам |

Использовать семантические CSS-переменные, а не разрозненные копии цветов и размеров. Дополнения для новых состояний вводить в единый слой токенов. Фотографии, иллюстрации, градиенты, стекло, размытие и декоративные анимации не использовать.

Проверять контраст текста: не менее 4.5:1 для обычного и 3:1 для крупного; интерактивных границ и значимых графических элементов — не менее 3:1. В частности, проверить белые подписи на оранжевых кнопках; при недостаточном контрасте затемнить заливку или изменить цвет текста в семантическом токене, сохранив направление дизайна. Не считать исходные токены автоматически прошедшими проверку доступности.

### 16.3. Компоненты и состояния

Создать переиспользуемые компоненты с едиными контрактами независимо от выбранного фреймворка:

- `Button`, `IconButton`, `Icon`: primary, secondary, strong, outline, ghost, danger; размеры 48/56/60px, loading, disabled, focus, hover, press и ошибка выполнения;
- `TextField`, `TextArea`: постоянная подпись, подсказка, ошибка, readonly, disabled, незавершённый ввод; текст не теряется при неудаче записи;
- `SegmentedControl`: 2–3 фильтра, выбранное состояние и управление клавиатурой;
- `TabBar`, `TopBar`: текущий раздел, возврат, доступные подписи и контекстное действие;
- `ActiveTrainingCard`, `MembershipStrip`, `Stat`, `ProgressSegments`, `SectionHeader`, `StepRow`, `StepCard`, `StatusLabel`, `ActionBar`, `HistoryRow` — по назначению исходных компонентов;
- `BottomSheet`: короткие формы и подтверждения; длинный редактор и разбор сложного конфликта — отдельные экраны;
- дополнительные компоненты состояния синхронизации, отчёта импорта, ошибки и разрешения конфликта в том же визуальном языке.

Один оранжевый главный призыв в области принятия решения; вторичное действие серое, следующее действие может быть чёрным. Опасное действие имеет текст о последствиях и подтверждение. Статус обозначается цветом, иконкой и словом. Disabled сопровождается понятной причиной, если она не очевидна.

Прогресс занятия: один сегмент на этап; выполненный — оранжевый, пропущенный — серый, неотмеченный — светлый. Высота 8px на белом и 10px в чёрном блоке. Пропуски не прибавляются к «Выполнено». Для большого числа этапов сегменты допускается переносить на строки; рядом всегда доступен текстовый итог. Числа разделов и этапов вычисляются из данных.

«Сейчас» — состояние навигации интерфейса для выбранного неотмеченного этапа, а не четвёртый сохраняемый статус отметки. `todo` из прототипа соответствует предметному `pending`.

### 16.4. Карта экранов

| Экран / сценарий | Обязательное содержание и действия |
| --- | --- |
| Главная, есть незавершённое занятие | Один чёрный главный блок с названием, количеством выполненных этапов, сегментами, текущим этапом и «Продолжить тренировку»; полоса абонемента и последние занятия |

| Нет доступного абонемента | Понятные варианты: нет абонемента, ещё не начался, истёк, исчерпан; создание при допустимости и доступ к истории/незавершённым занятиям |
| Занятие | TopBar с возвратом и «Завершить», название, план, выполнено, сегменты, полосы разделов, свёрнутые строки и раскрытый этап; нижняя панель действий; без TabBar |

| Программа и версии | Цель, заметки, полное содержание, номер версии; архив/восстановление, история версий, просмотр и восстановление старой как новой |
| Редактор | Название, цель, план, общие заметки; разделы и этапы со всеми полями, типом и optional; создание/удаление/перестановка, автосохранение черновика и отдельная публикация |

| Абонемент | Короткая форма создания/редактирования: начало, окончание, лимит 1/4/8, ошибки и последствия; сохранение всех ограничений раздела 4 |
| Настройки | Аккаунт и выход, абонемент и его редактирование, состояние синхронизации, резервное копирование/восстановление, установка PWA и фактическая версия выпуска |
| Вход / нет доступа | Wordmark ClimbPass, «Продолжить с Google», загрузка, ошибка, запрет доступа и повтор; соответствие требованиям выбранного OAuth-провайдера |

| Конфликты | Сущность и причина конфликта, локальная и серверная редакции, понятный выбор и экспорт; переход из статуса синхронизации |

В нижней навигации четыре раздела: «Главная», «Программы», «История», «Настройки». Смена названия вкладки «Тренировки» на «Программы» не меняет модель и не должна ломать прежние ссылки. Сохранить или перенаправить существующие hash-маршруты, включая посещение, выбор программы, редактор и версии; при изменении роутера задать таблицу совместимости.

Фильтр истории относится к занятиям: `completed` — завершённые, `active` — незавершённые, подпись «Идёт» допустима для активного. Отдельное состояние `unfinished` из демоданных в модель не добавляется. Посещения без тренировки и абонементы остаются доступны отдельными блоками, не выдаются за незавершённые занятия. Пустой результат фильтра сопровождается пояснением. После возврата из записи сохранять фильтр и позицию списка.

### 16.5. Взаимодействие с этапом и заметками

Свёрнутый этап отображает номер, название, метаданные и статус. Нажатие раскрывает задание во всю ширину содержимого, без дополнительной внешней карточки. В один момент раскрыт один этап; можно открыть любой, включая уже отмеченный. Полная инструкция доступна без обрезания.

Раскрытый этап показывает тип/статус, номер из общего числа, название, текстовые длительность и объём, инструкции, необязательность, прошлую заметку при наличии и личную заметку для типа `training`. Доступность заметки определяется `type`, а не индексом раздела.

Панель содержит «Пропустить» и «Выполнено» для неотмеченного этапа; для отмеченного — «Снять отметку» и переход к следующему неотмеченному. После успешной локальной отметки открывать следующий `pending` по порядку, затем искать с начала. Если таких нет, показывать итог и доступное завершение, но не завершать автоматически. Завершение также доступно в TopBar, даже если остались pending. Кнопку завершения в панели показывать в итоговом состоянии без раскрытого этапа, чтобы не подменять действие над текущим этапом.

Свайп вправо — выполнен, влево — пропущен, порог 90 CSS px. Повтор в ту же сторону снимает соответствующую отметку, сохраняя действующее поведение; противоположное направление меняет статус. Под этапом открывается чёрная подложка с подписью результата. Изменение происходит однократно по окончании жеста; короткий свайп, вертикальная прокрутка и `pointercancel` ничего не меняют. Жест не начинается из поля, кнопки или выделения текста. Все действия продублированы видимыми кнопками и доступны с клавиатуры.

Сохранение заметки и отметки не должно теряться из-за blur, смены этапа или навигации. Ошибка удерживает введённый текст, показывает «Не сохранено» и повтор. Не переключать этап как после успешной операции при ошибке локальной записи. Показывать разницу между «Сохранено на устройстве» и «Синхронизировано».

Редактор сохраняет черновик автоматически, публикация явно создаёт новую версию. «Закрыть» оставляет сохранённый черновик; действие «Отмена» допустимо только с точным объяснением его эффекта. Сброс черновика — отдельное подтверждаемое действие. Для перестановки предусмотреть кнопки вверх/вниз; drag-and-drop может их дополнять.

### 16.6. Офлайн, синхронизация и системные состояния

Для каждого экрана предусмотреть нормальное, пустое, загрузочное и ошибочное состояния, а для изменяемых данных — локальное сохранение, ожидание сервера и конфликт. Загрузка не подменяет непустую локальную историю пустым экраном.

Состояния синхронизации: «Синхронизировано», «Сохранено на устройстве · ожидает отправки», «Нет сети», «Синхронизация», «Нужно войти», «Ошибка синхронизации», «Есть конфликт». Статус ненавязчивый и доступен из настроек; требующие действия состояния дают переход к решению. Факт отсутствия сети не представляется ошибкой локального сохранения.

Новые экраны и сообщения используют те же токены и компоненты. Не сохранять текст прототипа «Все данные хранятся на этом устройстве» после появления сервера: объяснять локальную копию и синхронизацию. Не показывать успех импорта, пока соответствующий локальный или серверный этап фактически не завершён.

### 16.7. Адаптивность, клавиатура и доступность

- Контрольный мобильный размер — 390×844, без фиксированной рамки телефона в production. Проверяемые ширины: 320, 360, 390, 430, 768 и 1280px; горизонтальный скролл страницы отсутствует.
- На широком экране сохранить читаемую центральную колонку (ориентир до 720px); не растягивать мобильные элементы на всю ширину. Таблица сравнения конфликтов может использовать большую ширину с переходом в вертикальный вид на телефоне.
- Размеры кнопок 56/60px; минимальная интерактивная область 48×48px. В прототипе встречаются 40px IconButton и 44px сегменты — увеличить область до 48px без перекрытия соседних целей. Строки имеют минимальную, а не фиксированную высоту.
- Safe area брать из реального `env(safe-area-inset-*)`; демонстрационные 47/34px не навязывать устройствам без выреза. Не рисовать системный статус-бар и home indicator.
- Клавиатуру определять по реальному viewport/возможностям платформы. Не переносить заглушку клавиатуры и жёсткое смещение 291px. Заметка и действия должны оставаться видимыми; закрытие клавиатуры не оставляет пустой отступ.
- Фиксированные панели не закрывают последнюю строку, форму или ошибки; при нехватке высоты допускается прокрутка панели и содержимого.
- Кнопки-иконки имеют доступное имя, вкладка — выбранное состояние, раскрывающаяся строка — `aria-expanded`; прогресс сопровождается текстом. Декоративные иконки скрыты от скринридера.
- Модальный лист имеет заголовок, удержание фокуса, Escape, возврат фокуса, блокировку фоновых действий и доступную кнопку закрытия. Закрытие формы не теряет несохранённый ввод без предупреждения.
- Все действия доступны клавиатурой; focus видим и не обозначен только слабым изменением цвета. Увеличение текста до 200% не обрезает данные и кнопки.
- Возврат свайпа — до .22s ease, обновление прогресса — до .3s; без пружин и сжатия кнопок. Учитывать `prefers-reduced-motion`.

### 16.8. Иконки, ресурсы и сборка

Использовать единый набор Material Symbols Rounded: контурный по умолчанию, заполненный для выбранной вкладки, статуса и play. Размеры 16px для метаданных, 18–20px для подписей, 22–24px для кнопок, 26px для навигации. Эмодзи и Unicode-символы в роли иконок удалить. Знак приложения — текст «ClimbPass», Onest 800, трекинг −.03em.

Onest поставляется локально и включается в офлайн-оболочку. Иконки в исходной системе подключаются с Google Fonts; для production подготовить локальное подмножество используемых Material Symbols Rounded либо локальные глифы этого же набора с сохранением лицензии и внешнего вида. Критические иконки и подписи не должны зависеть от доступности CDN или показывать лигатурный текст вместо значка.

Не переносить загрузку React/Babel с unpkg, runtime-компиляцию JSX, `window.CP`, демонстрационный bootloader и тестовые данные как production-архитектуру. Ресурсы должны собираться или подключаться выбранным способом воспроизводимо, работать при ограниченной сети и соответствовать CSP. При использовании локальных глифов допустим SVG для иконок того же набора; декоративные SVG-иллюстрации не добавлять.

### 16.9. Тексты

Язык интерфейса — русский. Действия — глаголы в инфинитиве: «Продолжить тренировку», «Отметить посещение», «Снять отметку», «Сохранить новую версию». Статусы — факты с числами: «Выполнено 4 из 9 этапов», «Осталось 5 из 8 посещений». Последствия списания, удаления, замены и выхода сообщаются до подтверждения.

Системные обращения — на «вы», инструкции упражнения — на «ты» согласно стилю существующего содержания. При редизайне не переписывать пользовательские инструкции и заметки. Даты в чтении — словами, в списке день и сокращённый месяц; год виден из группировки или подписи. Поля ввода сохраняют точную календарную семантику. Исключить эмодзи, восклицания, мотивационные оценки, рейтинги, социальные и AI-элементы.

### 16.10. Расхождения прототипа и обязательная адаптация

| Найдено в исходных материалах | Решение для приложения |
| --- | --- |
| `App.jsx`: одно занятие, `restart`, `fresh`, локальное демосостояние | Реальные сущности и репозитории; никакого сброса истории или результатов при старте |
| `ProgramsScreen`: запрет другой программы до завершения текущей | Не вводить глобальный запрет: несколько незавершённых занятий допустимы в разных посещениях |
| `SettingsScreen`: новый абонемент заменяет текущий | Не переносить замену: создание запрещено при действующем абонементе; доступно его редактирование |
| `markVisit`: один флаг visited и прямое уменьшение остатка | Каждое посещение — отдельная запись; повтор дня подтверждается, остаток вычисляется |
| Числа 9 этапов, 3 раздела, 8 посещений, даты и тексты примера | Все значения берутся из реального состояния, включая исторические лимиты |
| Заметка определяется `section === 1`, редактор содержит readonly-поля | Определять по `step.type`, реализовать полный действующий редактор и черновики |
| История открывает только активную запись; нет всех старых маршрутов | Открывается любая запись, сохраняются версии, архив, посещения без тренировки, удаление и возобновление |
| Кнопка «Удалить все данные» | Не добавлять новый глобальный сброс/удаление аккаунта. Сохраняются существующие предметные удаления и подтверждённое восстановление из копии |
| StepCard не снимает отметку повторным свайпом, обрабатывает cancel как up | Сохранить действующее снятие и не выполнять действие при отменённом жесте |
| В описании нет вложенных карточек, но у прошлой заметки есть собственный блок | Не вкладывать большие карточки экрана; компактная заметка-подсказка допустима, как в StepCard |
| Фиксированный Device и рисованная клавиатура | Только демонстрация: реальные viewport, safe area и клавиатура |
| CDN шрифтов/библиотек, неполная доступность BottomSheet | Локальные ресурсы, production-подключение и доступное модальное поведение |

### 16.11. Порядок работ и результат редизайна

1. Зафиксировать источники, составить карту действующих маршрутов и состояний; дополнить её входом, переносом, синхронизацией и конфликтами.
2. Подготовить слой токенов и компоненты выбранной технологии, устранить проблемы контраста, размеров касания, модальности и внешних ресурсов.
3. Собрать проверяемые состояния на контрольных данных: главная, занятие с клавиатурой, программы/редактор, история, настройки; новые серверные состояния оформить в том же стиле.
4. Подключить компоненты к реальным операциям, не копируя демологику; проверить сохранение всех полей, маршрутов и действий.
5. Провести визуальную сверку с направлением «Страва», адаптивную и функциональную приёмку по разделу 13.5.

Результат: обновлённый интерфейс, переиспользуемые токены/компоненты, карта экранов и состояний, перечень обоснованных отклонений от исходников, сравнительные снимки и результаты проверок. Изменения выполняются в рамках этапа 7 раздела 12; подготовка карты и компонентов начинается раньше и не блокирует самостоятельную проверку миграции данных.
