# ClimbPass — память проекта

Актуализировано 31.10.2026 по локальному коду и документации. Реализованное поведение ниже отделено от запланированного. При расхождениях проверять текущий код; требования к будущим тренировкам находятся в `docs/training-specification.md`.

## Назначение и устройство

ClimbPass — персональное мобильное PWA для учёта абонементов и посещений скалодрома. Приоритет — iPhone и запуск с главного экрана; светлый интерфейс с оранжевым акцентом, нижней навигацией, адаптацией под мобильный экран.

Сейчас это статическое приложение без сервера данных, авторизации, сборщика, пакетных зависимостей и выделенного набора автоматических тестов. HTML, CSS и JavaScript находятся в `index.html`.

Основные файлы:

- `index.html` — интерфейс, абонементы, посещения, импорт/экспорт, установка и обновление PWA.
- `sw.js` — кеш ресурсов и офлайн-работа.
- `manifest.json`, `icon-192.png`, `icon-512.png` — установка приложения.
- `.github/workflows/deploy.yml` — SSH-деплой.
- `trainings.md` — исходные тексты двух тренировок.
- `docs/training-specification.md` — проект ТЗ на тренировки внутри посещений, ещё не реализованный.
- `memory.md` — эта сводка.

## Текущее хранение данных

Единственный используемый приложением ключ пользовательских данных — `localStorage.climb_pass`. Значение — JSON-массив абонементов:

```javascript
{
  id: 1234567890,        // Date.now(), целое число
  start: 'YYYY-MM-DD',
  end: 'YYYY-MM-DD',
  total: 8,
  visits: ['YYYY-MM-DD'],
  status: 'active'      // либо 'archived'
}
```

Посещения пока являются строками дат без собственных ID. Повторяющиеся даты допустимы. Отдельного хранилища `single_visits` и локальной аналитики `track()` в текущем коде нет. Разовое посещение представляется абонементом с `total: 1`; отдельной кнопки мгновенного разового прохода нет: сначала создаётся абонемент, затем отмечается посещение.

Не менять ключи и структуру без безопасной миграции. Обновление PWA не должно удалять пользовательские данные.

## Реализованные сценарии

- Создание абонемента: начало по умолчанию сегодня, окончание через 30 дней, лимит 1/4/8, по умолчанию 8. Кнопка — «Добавить абонемент». Проверяется наличие дат, порядок дат и отсутствие окончания в прошлом.
- Редактирование активного абонемента, отметка посещений и удаление с подтверждением.
- Повторное посещение сегодня разрешено после подтверждения.
- `activePass()` выбирает первый абонемент со статусом `active`.
- Дата окончания включается в срок. `isFinished()` считает абонемент завершённым, когда `end < today()` или израсходован лимит. `archiveCheck()` вызывается при отрисовке и архивирует текущий абонемент.
- `deletePassVisit(passId, visitIndex)` удаляет посещение из конкретного абонемента; исходные индексы сохраняются при сортировке через `sortedVisits()`.
- Посещения архивного абонемента нельзя удалять при наличии действующего: ограничение есть в интерфейсе и обработчике. Без действующего удаление доступно. Если после удаления архивный абонемент больше не завершён, он снова становится активным.

Даты хранятся как локальные календарные строки `YYYY-MM-DD`. `today()` использует локальные компоненты даты, а не UTC через `toISOString()`. Отображение — `ДД.ММ.ГГГГ`, через перестановку частей строки. Не возвращать ошибку с предыдущим днём из-за UTC.

## Экраны и история

Нижняя навигация сейчас содержит три экрана:

- `#home` — карточка действующего абонемента и его посещения; при отсутствии действующего — форма создания.
- `#history` — завершённые абонементы с посещениями внутри каждого. Абонементы сортируются по началу от новых к старым, затем по ID. При действующем абонементе архивные посещения показываются компактным списком без удаления.
- `#settings` — экспорт/импорт, инструкция установки, контакт и версия приложения.

Старый адрес `#archive` перенаправляется на экран истории. Отдельный экран архива объединён с историей. Текущая история НЕ является единым хронологическим списком всех посещений: действующие находятся на главной, завершённые — в истории с группировкой по абонементам. Единая история предусмотрена будущим ТЗ.

Старые утверждения этой памяти о сломанном удалении через `deleteVisit(i)`, обязательном `getAllVisits()`, случайной надписи кнопки и отдельном блоке архива больше не описывают текущую реализацию.

## Резервное копирование сейчас

Экспортирует весь массив абонементов как JSON в буфер обмена; при недоступности копирования показывает поле для ручного выделения. Скачиваемый файл пока не реализован.

Импорт — вставка JSON в поле настроек. Проверяются массив, ожидаемые поля и типы, формат строк дат, положительный целый лимит, допустимый статус. При наличии текущих данных требуется подтверждение полной замены. Импорт выбирает только ожидаемые поля.

Текущая проверка дат ограничена форматом, уникальность ID и наличие нескольких активных абонементов не проверяются. Начальное чтение JSON и запись в localStorage не защищены полноценной обработкой повреждения данных/нехватки места. Усиленная валидация и обработка ошибок — требования будущей реализации, не готовые возможности.

## PWA и выпуск обновлений

Локальная версия кеша в `sw.js` — `25.8`. App shell включает корень, HTML, manifest, обе иконки и service worker. HTML использует network-first с офлайн-возвратом из кеша; прочие GET-ресурсы — возврат из кеша с фоновым обновлением либо сеть. Кешируются успешные ответы.

На установке вызывается `skipWaiting()`, при активации удаляются другие кеши и вызывается `clients.claim()`. Клиент регистрирует worker, проверяет обновление и после смены существовавшего контроллера перезагружается с уведомлением; первый захват страницы не считается обновлением. Протокол сообщений `SKIP_WAITING` сейчас не нужен и не реализован.

При изменении ресурсов обновлять версию кеша. При будущем разделении на модули обеспечить согласованность версий HTML/CSS/JS и добавить ресурсы в app shell. Текущее поведение само по себе не доказывает атомарное обновление будущих модулей.

Manifest: standalone, portrait, `start_url` и `scope` — `/`. Название ClimbPass, theme color `#ef652f`, background `#f6f7f9`. Инструкция установки доступна в настройках.

## Запланировано: тренировки внутри посещений

Статус на 31.10.2026: есть исходные программы и проект ТЗ; код тренировок, миграция и новый редактор ещё не реализованы. Полное описание и критерии приёмки — `docs/training-specification.md`.

Основные правила для продолжения работы:

1. Тренировка существует только внутри уже зарегистрированного посещения; не более одной на посещение. Посещение без тренировки допустимо. Запуск/продолжение/завершение не списывают ещё один проход.
2. Каждое посещение получает постоянный ID. Одинаковые даты сохраняются как независимые записи со своими результатами.
3. Две исходные программы из `trainings.md`: «Сила и техника в нависании» и «Маршруты и расширение уровня 6b», обе по 90 минут. Перенести все исходные инструкции и ограничения без добавления новых рекомендаций.
4. Прохождение: этапы «Не выполнен», «Выполнен», «Пропущен», заметки, немедленное автосохранение, продолжение после закрытия/офлайн. Пропуск не считается выполнением. Завершение возможно с незаполненными этапами после подтверждения. Возобновление сохраняет отметки и очищает время завершения.
5. Программы имеют постоянные ID, неизменяемые сохранённые версии и отдельные автосохраняемые черновики. Новые занятия используют последнюю сохранённую версию. Начатые и прошлые занятия хранят снимок исходного содержания. Восстановление версии создаёт новую; архивирование программы сохраняет историю и допускает восстановление.
6. Результаты находятся внутри посещений. Единая история включает действующий и архивные абонементы и разовые проходы. Архивирование абонемента не блокирует продолжение тренировки. Существующее ограничение удаления архивных посещений при действующем абонементе сохраняется; удаление посещения с тренировкой требует предупреждения о потере результатов.
7. Безопасная повторяемая миграция сохраняет все посещения, включая дубли дат, и старый ключ до подтверждённого перехода. Не создавать вымышленные времена исторических тренировок, не перезаписывать пользовательские программы начальными. Ошибки данных и записи должны сохранять исходное состояние.
8. Новый экспорт — скачиваемый полный JSON с версией формата, датой, всеми версиями, черновиками и результатами. Импорт нового и старого формата — полная проверка перед заменой, подтверждение, без слияния. Старый массив не содержит тренировок.
9. Разделить код на модули хранения/миграций, абонементов/посещений, программ/версий, прохождения, импорта/экспорта и отображения; вынести стили. Навигация должна получить экран «Тренировки». Все сценарии работают офлайн.
10. В первую версию не входят сервер, регистрация, синхронизация, календарный план, таймеры, автоматические рекомендации, учёт каждого повторения и создание произвольного числа новых программ.

Перед завершением реализации нужны проверки миграции, связей и версий, учёта проходов, полного восстановления копии, неверных данных, а также сквозные сценарии интерфейса, обновления и офлайн-работы на мобильном экране.
